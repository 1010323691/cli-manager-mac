# 状态查询审计

## 本机复现

用同一 Codex 可执行文件和同一 PATH，在这台 Mac 的两种执行环境各发起一次本地 `initialize` RPC。两次均使用隔离的无账号配置，未发出模型请求。

| 执行环境 | 观察结果 |
| --- | --- |
| 正常 macOS 进程 | 约 193 ms 完成初始化，关闭时退出码 0 |
| 受限执行进程 | 约 45–59 ms 在初始化完成前退出，退出码 1，stderr 包含 OS 权限限制 |

两边均使用同一已安装的 Codex Node.js 启动器。两边 PATH 都先搜索 `~/.local/bin`、`/opt/homebrew/bin` 和 `/usr/local/bin`，再搜索系统目录。对照中没有观察到 DNS 或连接错误。受限进程报告过无法创建 PATH 别名。该警告本身表明流程曾继续，不能单独证明最后被拒绝的是哪次系统调用。

原 App Server 客户端在收不到初始化回复时等待 RPC 的 12 秒窗口，并抛出 `RuntimeError`。旧 CLI 将探测异常写成 `probe_error` 和用于调度保护的 `logged_in=false`。这个路径解释了为何该环境下不能得出账户状态。它无法为没有保留底层诊断的历史记录逐条归因。已存在的额度记录只读检查，仍可显示提供方已确认的额度封锁与重置时刻。

## 正常应用、缓存和按钮

1. 签名应用选择 Python 3.11+，把专用解释器和桥接器的绝对路径作为参数传给后台 `Process`。桥接器按实例注册的二进制路径或应用 PATH 查找提供方，既有实例环境继续限制继承变量。Swift 手动探测进程的总期限为 125 秒，原 CLI 的 Codex RPC 按阶段使用各自的 12 秒窗口。
2. 「读取本地状态」只消费 SQLite 当前快照。「查询提供方」和「重试查询」显式调用对应实例的 CLI。应用也会按启动、实例使用和额度重置事件自动查询。Mac 签名预览用隔离提供方验证了初始化错误、重新读取保持旧结论、显式重试变为已登录且额度为 76%，以及外部写入被轮询读到。
3. 写入使用原实例锁。若查询中的账户代次或失效计数改变，原引擎废弃本次结果，桥接器返回未提交。Swift 在一次读取期间收到更新请求时再读一次，过时的完成结果不会发布到界面。
4. 失败时仍保留调度保护。新适配层为同一账户代次保存最近一次已证实的登录状态和时间。诊断仅保存阶段、分类与耗时，不保存原始 stderr。可信的现有额度封锁可以与查询失败并存，普通历史百分比不会被当成当前额度。没有保存过的历史确认时间无法从旧失败记录恢复。

按钮、外部状态变化和 PTY 界面的验证使用隔离实例。真实账户未被用于交互式模型或权限验收。
